# 监管报送指标血缘影响分析设计

> 更新日期：2026-05-18  
> 适用项目：监管报送项目  
> 文档定位：定义一套通用的监管报送变更影响分析框架。1104 作为一阶段落脚点，后续 EAST、客户风险、一表通等报送体系复用同一套“监管对象定位 - 指标口径 - 血缘映射 - 影响分析 - 工单沉淀”方法。

## 1. 设计结论

本项目主线应从“识别监管发文影响哪些业务对象”升级为“识别监管报送变更影响哪些监管报送对象、指标口径、报送系统字段、源系统字段和处理工单”。

建议统一主流程：

```text
监管变更材料导入
  -> 监管报送对象定位
  -> 指标/字段/口径差异识别
  -> 报送系统血缘定位
  -> 源系统字段和加工逻辑影响分析
  -> 工单草稿生成
  -> 人工确认与处理归档
  -> 经验沉淀为规则、映射和案例
```

这里的“监管变更材料”不只包括正式公告，也包括填报说明、表样、监管会议纪要、监管答疑、邮件通知、年度制度附件和内部口径确认记录。

前端现有“上传发文 -> 条款证据 -> 语义识别 -> 影响分析 -> 规则与工单”的流程可以保留，不需要大改。需要调整的是后端判断逻辑：从通用条款影响判断，升级为面向监管报送体系的结构化定位和血缘影响分析。

## 2. 通用适用范围

1104 是一阶段样板，不是系统边界。系统应抽象出通用的监管报送模型，支持后续扩展：

| 报送体系 | 一阶段/后续 | 主要特征 | 复用方式 |
|---|---|---|---|
| 1104 非现场监管报表 | 一阶段落脚点 | 报表、行列项目、指标口径、频度、机构范围、汇总加工 | 重点验证报表指标建模、口径差异和报送系统血缘 |
| EAST | 后续扩展 | 明细表、数据项、接口标准、字段采集、数据质量校验 | 复用字段定位、源系统血缘、校验规则和工单沉淀 |
| 客户风险 | 后续扩展 | 客户、集团、授信、风险暴露、关联关系 | 复用主体识别、主数据映射、风险维度和跨表校验 |
| 一表通 | 中长期主线 | 明细数据标准、可信区、资源层/穿透层/指标层、转换验证 | 作为统一监管数据底座，承接 1104/EAST/客户风险的映射和替代验证 |
| 区域特色报表 | 后续补充 | 地方监管差异、机构适配、低频补录 | 复用版本、适用范围、补录字段和工单模板 |

通用抽象是：

```text
监管报送体系
  -> 监管报送对象
  -> 报送字段/指标
  -> 口径规则
  -> 报送系统映射
  -> 源系统血缘
  -> 质量校验
  -> 工单与经验
```

## 3. 监管报送对象建模

### 3.1 为什么不能只建“字段”

监管报送中的“字段”有多种形态：

| 体系 | 字段形态 | 示例 |
|---|---|---|
| 1104 | 报表单元格/指标项目 | G24 同业融入余额、G21 期限缺口 |
| EAST | 明细表字段 | 客户信息表客户号、贷款合同表合同编号 |
| 客户风险 | 客户/集团/风险暴露维度字段 | 集团客户编号、授信额度、风险暴露余额 |
| 一表通 | 数据采集项、维度明细、指标层字段 | 资源层明细字段、穿透层宽表字段、指标层加工项 |

因此，系统底层不应把所有对象都压成普通字段，而应统一建模为“监管报送对象”和“报送项”。

### 3.2 核心对象

| 对象 | 说明 | 1104 示例 | EAST 示例 |
|---|---|---|---|
| `reporting_system` | 报送体系 | 1104 | EAST |
| `reporting_version` | 制度版本 | 2025 年 251 版 | 某年度 EAST 数据标准版本 |
| `reporting_object` | 报送对象 | G21、G24、G25 | 客户信息表、贷款合同表 |
| `reporting_section` | 分部/子表/表页 | G25 第 I 部分 | EAST 某主题域 |
| `reporting_item` | 报送项 | 某行列交叉指标 | 某明细字段 |
| `reporting_dimension` | 维度 | 机构、币种、行业、五级分类、企业规模 | 客户类型、产品类型、交易类型 |
| `reporting_rule` | 口径规则 | 统计范围、排除项、汇总公式 | 字段取值规则、必填规则、码值规则 |

对 1104，`reporting_item` 的最小粒度建议是：

```text
报表编号 + 分部 + 行项目 + 列项目 + 单元格/指标代码 + 版本
```

对 EAST，`reporting_item` 的最小粒度建议是：

```text
主题域 + 明细表 + 字段名 + 字段版本
```

### 3.3 建议数据表

```text
reg_reporting_system
reg_reporting_version
reg_reporting_object
reg_reporting_section
reg_reporting_item
reg_reporting_dimension
reg_reporting_item_dimension
reg_reporting_rule
reg_reporting_rule_condition
reg_reporting_instruction
```

首期可以不一次建全，但模型设计应按这套抽象保留扩展空间。

## 4. 1104 一阶段建模方式

1104 一阶段选取资金同业相关样板表，不做全量实现。选择这一组的原因是它能同时覆盖流动性风险、同业负债、投资资产、交易对手维度、期限维度和跨表一致性校验，便于验证“报送指标 -> 报送字段 -> 源字段/维度字段”的血缘影响分析。

| 优先级 | 样板 | 原因 |
|---|---|---|
| P0 | G24 最大百家金融机构同业融入情况表 | 直接体现同业融入余额、交易对手金融机构识别、产品范围和到期日等口径 |
| P0 | G21 流动性期限缺口统计表 | 与期限、现金流、同业头寸和流动性缺口加工相关 |
| P0 | G25 流动性覆盖率和净稳定融资比例情况表 | 与合格优质流动性资产、现金净流出和稳定资金口径相关 |
| P1 | G27 主要负债项目明细表 | 与同业存放、主要负债结构和 G24 口径校验相关 |
| P1 | G31 投资业务情况表第 I 部分：底层资产投资情况 | 与债券投资、底层资产和投资业务数据源相关 |

1104 的建模层级：

```text
1104 制度版本
  -> 报表目录
  -> 报表分部
  -> 行项目/列项目
  -> 指标单元格
  -> 填报说明/口径规则
  -> 报送系统字段
  -> 加工逻辑/数据血缘
```

示例：

```text
G24 最大百家金融机构同业融入情况表
  -> 最大百家金融机构同业融入余额
  -> 交易对手金融机构、同业负债产品、余额、到期日
  -> 报送系统字段 rpt_g24.interbank_borrowing_bal_top100
  -> 加工逻辑 job_rpt_g24_interbank_monthly
  -> 数据集市字段 dm_interbank_position.balance
  -> 源系统字段 interbank_deal.balance / interbank_deal.counterparty_fin_org_code / counterparty.institution_type
```

## 5. 血缘定位模型

### 5.1 血缘链路

监管报送影响分析必须支持多段血缘，而不是只记录“影响某系统”。

推荐链路：

```text
监管报送项
  -> 报送系统字段
  -> 报送加工表/结果表
  -> 数据集市/主题宽表字段
  -> ODS/贴源字段
  -> 源系统表字段
  -> 码值/主数据/维度表
  -> ETL/调度任务/校验任务
```

### 5.2 血缘对象

| 对象 | 说明 |
|---|---|
| 报送系统字段 | 报送平台中实际承载报表指标或明细报送项的字段 |
| 加工任务 | SQL、ETL、存储过程、调度任务、数据加工配置 |
| 中间表字段 | 数据集市、监管报送主题层、汇总表字段 |
| 源系统字段 | 信贷、核心、客户、总账、押品、资金、同业、卡系统等源字段 |
| 维度/码值 | 企业规模、行业分类、五级分类、贷款品种、客户类型等映射 |
| 校验规则 | 表内、表间、跨期、跨体系、一表通/1104/EAST 差异校验 |

建议表：

```text
data_system_catalog
data_table_catalog
data_field_catalog
etl_job_catalog
lineage_node
lineage_edge
reporting_item_lineage
code_mapping_catalog
quality_rule_catalog
```

### 5.3 血缘证据

每条血缘关系都应带证据和状态，不能只存一条静态映射。

| 字段 | 说明 |
|---|---|
| `evidence_type` | SQL 解析、ETL 配置、人工确认、历史工单、数据字典、会议纪要 |
| `evidence_ref` | 证据文件、工单号、SQL 任务、确认记录 |
| `confidence` | 高、中、低 |
| `review_status` | 待确认、已确认、已废弃 |
| `effective_from` / `effective_to` | 生效版本或时间范围 |

这点很重要：监管报送血缘不是一次性资产，而是持续变化的知识资产。

## 6. 监管变更识别逻辑

### 6.1 输入材料类型

| 类型 | 示例 | 处理重点 |
|---|---|---|
| 正式通知 | 年度报表填报工作通知 | 识别制度版本、报送范围、时间要求 |
| 表样 | Excel / WPS 表样 | 识别行列结构、指标项、增删改 |
| 填报说明 | Word / WPS / PDF | 识别指标定义、统计口径、排除项、特殊说明 |
| 会议纪要 | 监管会议说明、业务讨论纪要 | 识别人工解释、待确认问题和口径结论 |
| 监管答疑 | 邮件、问答、补充说明 | 识别口径补丁、例外规则 |
| 内部工单 | 历史需求、开发、测试、验收记录 | 复用历史判断和血缘经验 |

### 6.2 变更类型

| 类型 | 示例 | 后续影响 |
|---|---|---|
| 报表新增 | 新增 S74 数字领域相关情况统计表 | 新建报表对象、指标、字段、任务 |
| 报表停报 | 某机构特色表取消 | 停止任务、归档映射 |
| 行列项目调整 | 某报表新增行或列 | 新增或修改报送项、加工字段、校验 |
| 指标口径调整 | 普惠型小微企业认定范围变化 | 影响筛选条件、码值映射、源字段 |
| 机构范围调整 | 某类机构新增填报 | 影响任务生成和机构适用规则 |
| 频度/时限调整 | 月报改季报、6 天改 13 天 | 影响报送日历和调度 |
| 校验规则调整 | 新增表间一致性校验 | 影响质量规则和测试 |
| 码值/主数据调整 | 行业分类、企业规模、产品分类调整 | 影响维表、源系统采集和历史数据处理 |

### 6.3 AI 与后端分工

| 环节 | AI 做什么 | 后端做什么 |
|---|---|---|
| 文本解析 | 识别报表编号、指标名称、监管动作、口径描述 | 保存原文、位置、附件结构 |
| 候选定位 | 基于语义召回可能涉及的报送对象和报送项 | 用结构化目录、别名、版本过滤候选 |
| 差异解释 | 对比新旧说明，解释口径差异 | 计算文件版本差异、行列结构差异 |
| 血缘影响草拟 | 根据候选血缘生成影响说明和待确认问题 | 从血缘库查可信候选，不允许 AI 发明字段 |
| 工单草拟 | 生成不同责任团队可读的工单正文 | 控制工单类型、状态、责任团队和关联关系 |
| 经验复用 | 总结历史案例相似点 | 检索已确认历史工单、规则和映射 |

底线：

```text
AI 不直接决定最终口径。
AI 不直接生成生产 SQL 并发布。
AI 不直接发明内部表字段。
AI 的结论必须带证据、置信度和待确认问题。
```

## 7. 影响分析设计

### 7.1 分析步骤

```text
1. 识别变更材料类型和制度版本
2. 抽取变更条款/表样差异/填报说明差异
3. 定位监管报送体系和报送对象
4. 定位报送项或候选报送项
5. 召回现有口径规则和历史处理案例
6. 召回报送系统字段和数据血缘
7. 判断影响类型、范围和置信度
8. 生成待确认问题和处理建议
9. 生成人工复核和实施工单草稿
10. 处理完成后沉淀经验
```

### 7.2 影响类型

| 类型 | 判断问题 | 工单倾向 |
|---|---|---|
| 报表结构影响 | 是否新增/删除/修改报表、行、列、字段 | 报表配置/表样改造工单 |
| 指标口径影响 | 统计范围、过滤条件、排除项是否变化 | 口径确认 + 加工逻辑改造工单 |
| 机构范围影响 | 哪些机构需要新增或取消填报 | 报送任务/机构范围配置工单 |
| 源系统字段影响 | 现有源字段是否足够 | 源系统改造/数据采集工单 |
| 加工逻辑影响 | SQL、ETL、汇总、维表映射是否要改 | 报送加工工单 |
| 校验规则影响 | 表内、表间、跨期、跨体系校验是否变化 | 数据质量规则工单 |
| 补录流程影响 | 是否需要新增人工补录、凭证或复核 | 补录页面/运营流程工单 |
| 历史数据影响 | 是否需要追溯重算、补报、差异说明 | 数据修正/监管解释工单 |

### 7.3 影响分析输出

每个影响项建议结构化保存：

```text
影响项 ID
变更来源
报送体系
制度版本
涉及报送对象
涉及报送项
变更类型
原口径
新口径
受影响报送字段
受影响源系统/表/字段
受影响加工任务
受影响校验规则
影响原因
证据片段
置信度
处理建议
待确认问题
复核状态
```

处理结果建议分为：

| 结果 | 含义 | 后续动作 |
|---|---|---|
| 明确影响 | 变更明确，且命中已确认报送项和血缘 | 生成实施工单 |
| 可能影响 | 命中候选报送项或候选血缘，但证据不足 | 生成人工确认工单 |
| 仅作参考 | 有背景价值，不触发系统改造 | 归档 |
| 不相关 | 不属于当前报送体系或机构范围 | 过滤 |
| 待补充材料 | 需要会议纪要、监管答疑或人工口径补充 | 挂起并提示补充 |

## 8. 工单设计

### 8.1 工单不应只等于 SQL 工单

SQL 工单仍有必要，但不能作为项目主线。监管报送变更往往同时涉及业务口径、数据映射、源系统采集、报送加工、校验规则、测试验收和归档。因此，SQL 应作为“报送加工工单”或“校验工单”中的技术内容，而不是唯一产物。

推荐工单类型：

| 工单类型 | 责任方 | 内容 |
|---|---|---|
| 口径确认工单 | 监管报送/业务人员 | 确认指标含义、适用范围、是否追溯、特殊口径 |
| 数据映射工单 | 数据治理/报送人员 | 确认报送项到报送字段、源字段、码值维表的映射 |
| 报送加工工单 | 报送系统/数据开发 | 修改 SQL、ETL、调度、汇总逻辑 |
| 源系统改造工单 | 源系统团队 | 新增采集字段、调整码值、补充接口 |
| 校验规则工单 | 数据质量/报送团队 | 新增或修改表内、表间、跨体系校验 |
| 测试验收工单 | 业务 + 科技 | 准备样例、回归测试、差异分析、验收确认 |
| 归档复盘工单 | 报送管理人员 | 记录最终口径、处理结论、监管反馈和经验 |

### 8.2 工单字段

```text
工单标题
工单类型
变更来源
涉及报送体系
涉及报送对象/报送项
影响类型
当前血缘定位
建议处理动作
证据片段
待确认问题
验收标准
关联影响项
关联历史案例
处理结论
人工确认记录
归档标签
```

### 8.3 SQL 在工单中的定位

AI 可以生成：

```text
候选 SQL 修改点
差异分析 SQL
数据探查 SQL
校验 SQL
回归测试 SQL
```

AI 不应直接生成并发布生产 SQL。更稳妥的方式是：

```text
AI 给出可审查 SQL 建议
  -> 开发确认
  -> 测试环境执行
  -> 差异分析
  -> 业务验收
  -> 发布归档
```

## 9. 经验沉淀

工单关闭后必须反哺知识库，否则系统无法减少下一次沟通。

沉淀对象：

| 对象 | 内容 |
|---|---|
| 报送项映射 | 某报送项最终对应哪些报送字段和源字段 |
| 口径规则 | 业务人员确认后的统计口径、排除项、特殊说明 |
| 血缘证据 | 哪条 SQL、ETL、数据字典或人工记录证明了映射 |
| 校验规则 | 表内、表间、跨期、跨体系校验方法 |
| 历史案例 | 类似变更当时如何判断、如何改造、谁确认 |
| 待问问题模板 | 某类变更通常需要向业务/科技/监管确认什么 |
| 工单模板 | 不同影响类型对应的工单正文和验收标准 |

经验沉淀后的复用链路：

```text
新监管变更
  -> 命中相似报送项/相似口径
  -> 召回历史影响项和工单
  -> 复用已确认血缘和待确认问题
  -> 生成更准确的影响分析和工单草稿
```

## 10. 后端判断逻辑调整

现有后端可以保留“文档、任务、条款、语义、影响、工单”框架，但判断逻辑需要升级。

### 10.1 当前逻辑

```text
条款证据
  -> AI 抽取监管语义
  -> 识别报送对象和报送项
  -> 候选字段映射
  -> 影响分析
  -> 规则卡片/工单
```

### 10.2 新逻辑

```text
监管变更证据
  -> 识别报送体系
  -> 识别报送对象
  -> 识别报送项/指标/字段
  -> 识别口径差异
  -> 召回报送项血缘
  -> 定位报送系统字段和源系统字段
  -> 分析影响类型
  -> 生成分层工单
  -> 沉淀人工确认经验
```

### 10.3 建议新增后端能力

| 能力 | 说明 |
|---|---|
| 报送体系目录服务 | 管理 1104/EAST/客户风险/一表通等报送体系 |
| 报送对象和报送项服务 | 管理报表、表页、指标、字段、维度 |
| 口径规则服务 | 管理填报说明、指标定义、筛选条件、码值规则 |
| 血缘服务 | 管理报送项到报送字段、源字段、ETL、校验规则的多段映射 |
| 变更识别服务 | 从公告、表样、填报说明、会议纪要中抽取变更对象 |
| 影响分析服务 | 结合口径、血缘、历史案例输出影响项 |
| 工单生成服务 | 按影响类型生成不同责任团队的工单草稿 |
| 经验归档服务 | 将人工确认结果回写为规则、映射和案例 |

## 11. 前端影响判断

你的判断是对的：前端“上传发文到工单草稿”的主流程不用大改。

建议保留五步流程：

```text
上传发文
  -> 条款证据
  -> 语义识别
  -> 影响分析
  -> 规则与工单
```

但每一步的展示内容需要逐步换芯：

| 前端步骤 | 原展示重点 | 新展示重点 |
|---|---|---|
| 上传发文 | 发文摘要、任务画像 | 变更材料类型、报送体系候选、制度版本候选 |
| 条款证据 | 监管条款片段 | 变更证据：条款、表样差异、填报说明差异、会议纪要片段 |
| 语义识别 | 主体、业务、动作、对象 | 报送体系、报送对象、报送项、口径动作、机构范围 |
| 影响分析 | 业务对象、系统、字段影响 | 报送字段、源系统字段、加工任务、校验规则、置信度、待确认问题 |
| 规则与工单 | 规则卡片、工单草稿 | 口径确认、数据映射、报送加工、源系统改造、校验、测试、归档等组合工单 |

所以前端改动属于“内容和字段升级”，不是流程重做。首期可以先在现有页面上增加 1104/报送体系相关字段，不必重画产品结构。

## 12. 一阶段实施边界

为了可落地，一阶段建议控制范围：

| 范围 | 建议 |
|---|---|
| 报送体系 | 先做 1104，模型按通用报送体系设计 |
| 样板报表 | 优先 G24/G21/G25，再补 G27/G31 |
| 血缘深度 | 至少做到“报送项 -> 报送字段 -> 源系统字段/码值维表”，ETL 任务可先用样例 |
| AI 能力 | 做变更识别、候选定位、影响说明、工单草拟，不做自动发布 |
| 工单 | 先生成草稿和归档，不必对接真实工单系统 |
| SQL | 做差异分析 SQL/校验 SQL 建议，不做生产 SQL 自动改造 |
| 人工确认 | 必须保留，确认结果回写知识库 |

一阶段成功标准：

```text
上传一份 1104 变更材料
  -> 系统识别涉及的报表/指标/口径
  -> 定位候选报送系统字段和源系统字段
  -> 输出影响原因、置信度和待确认问题
  -> 生成分类型工单草稿
  -> 人工确认后形成可复用历史案例
```

## 13. 对外表述

推荐表述：

> 本项目不是简单的监管发文摘要工具，而是面向监管报送变更的影响分析与落地辅助平台。系统将监管公告、表样、填报说明和会议纪要中的变更要求，定位到具体报送对象和报送项，再结合内部报送系统字段、源系统血缘、历史工单经验和校验规则，生成可复核的影响分析和分类型工单草稿，帮助减少反复人工沟通，并把人工判断经验沉淀为可复用的监管报送知识资产。

更短版本：

> 以 1104 为一期样板，构建一套可扩展到 EAST、客户风险和一表通的监管报送变更影响分析框架，核心能力是“报送项定位、血缘穿透、影响判断、工单生成、经验沉淀”。
