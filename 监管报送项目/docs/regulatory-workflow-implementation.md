# 监管报送变更流程化加工与影响判定设计

> 更新日期：2026-05-18  
> 适用项目：监管报送变更影响分析与工单助手 / 监管报送项目  
> 文档定位：记录项目主线设计。当前主线已从“监管发文条款到业务对象影响”调整为“监管报送变更到报送项、指标口径、数据血缘和工单沉淀”的通用影响分析框架。1104 作为一阶段落脚点，后续 EAST、客户风险、一表通等报送体系复用同一套方法。

## 1. 设计基线

项目前端主流程继续采用五步流程化设计：

```text
上传发文
  -> 条款证据
  -> 语义识别
  -> 影响分析
  -> 规则与工单
```

该流程不需要推倒重做，但每一步的底层含义需要升级。原设计偏向“上传监管发文后识别条款影响哪些业务对象、字段和系统”；新设计面向监管报送场景，重点识别监管材料中的报表、字段、指标、口径、机构范围、报送频度、校验规则等变化，再通过监管报送血缘定位到报送系统字段、源系统字段、加工任务和质量校验规则。

新的主流程可以概括为：

```text
监管变更材料导入
  -> 监管报送对象定位
  -> 指标/字段/口径差异识别
  -> 报送系统血缘定位
  -> 源系统字段和加工逻辑影响分析
  -> 工单草稿生成
  -> 人工确认与处理归档
  -> 经验沉淀为规则、映射和案例
```

前端仍展示“上传发文到工单草稿”的五步流程；后端判断逻辑从通用条款影响判断，升级为面向监管报送体系的结构化定位和血缘影响分析。

一阶段以 1104 非现场监管报表为落脚点，但模型必须保持通用，后续可扩展到 EAST、客户风险、一表通和区域特色报表。

## 2. 三层资产结构

底层资产按三层理解：

```text
证据层：监管制度 + 变更证据
定位层：报送对象 + 报送项 + 指标口径 + 数据血缘
落地层：影响项 + 工单草稿 + 校验规则 + 经验归档
```

| 层级 | 包含资产 | 核心问题 | 当前相关表 |
|---|---|---|---|
| 证据层 | 正式通知、表样、填报说明、会议纪要、监管答疑、历史工单 | 监管变化依据是什么 | `reg_documents`、`reg_clauses`，后续扩展表样差异和会议纪要证据 |
| 定位层 | 报送体系、报送对象、报送项、指标口径、维度、数据血缘 | 变化具体落到哪个监管报送项，内部哪些字段和加工逻辑可能受影响 | `reg_reporting_systems`、`reg_reporting_versions`、`reg_reporting_objects`、`reg_reporting_sections`、`reg_reporting_items`、`reg_reporting_instructions`、`reg_reporting_rules`、`data_system_catalog`、`data_field_catalog`、`reporting_item_lineage` |
| 落地层 | 影响项、工单草稿、校验规则、人工确认、历史案例 | 谁来确认、怎么改、怎么验收、经验如何复用 | `reg_reporting_change_candidates`、`reg_reporting_impact_items`、`ticket_drafts`、`review_records` |

其中，早期 `business_object_dict`、`metadata_fields`、`object_field_mappings` 不再作为主线入口。后端判断逻辑以监管报送对象/报送项为入口，再通过 `reporting_item_lineage` 定位内部报送字段、数据集市字段、源系统字段和维度/过滤字段。

## 2.1 通用报送体系抽象

通用模型如下：

```text
监管报送体系
  -> 监管报送对象
  -> 报送字段/指标
  -> 口径规则
  -> 报送系统映射
  -> 源系统血缘
  -> 质量校验
  -> 工单与经验
```

| 报送体系 | 一阶段/后续 | 主要特征 | 复用方式 |
|---|---|---|---|
| 1104 非现场监管报表 | 一阶段落脚点 | 报表、行列项目、指标口径、频度、机构范围、汇总加工 | 重点验证报表指标建模、口径差异和报送系统血缘 |
| EAST | 后续扩展 | 明细表、数据项、接口标准、字段采集、数据质量校验 | 复用字段定位、源系统血缘、校验规则和工单沉淀 |
| 客户风险 | 后续扩展 | 客户、集团、授信、风险暴露、关联关系 | 复用主体识别、主数据映射、风险维度和跨表校验 |
| 一表通 | 中长期主线 | 明细数据标准、可信区、资源层/穿透层/指标层、转换验证 | 作为统一监管数据底座，承接 1104/EAST/客户风险的映射和替代验证 |
| 区域特色报表 | 后续补充 | 地方监管差异、机构适配、低频补录 | 复用版本、适用范围、补录字段和工单模板 |

## 3. 与 RAG 的关系

本项目可以使用 RAG，但整体不应被定义为普通 RAG 问答系统。

| 对比项 | 普通 RAG | 本项目流程化加工 |
|---|---|---|
| 核心目标 | 找到相关片段并回答问题 | 将监管变更材料加工成可解释的报送影响分析，并沉淀血缘、规则与工单草稿 |
| 主要产物 | 回答、摘要、引用片段 | 变更证据、报送对象定位、血缘影响分析、规则卡片草稿、工单草稿 |
| 中间结果 | 通常只保留 chunk 和向量 | 每一步加工结果都入库并可复核 |
| 适用位置 | 相似材料召回、历史工单召回、依据检索 | 作为辅助能力贯穿流程，不作为产品主线 |

推荐表达：

```text
RAG 负责“找得到”，监管规则加工流程负责“落得下去”。
```

## 4. 五步流程设计

### 4.1 上传发文

目标：登记监管材料来源，完成基础解析，并创建后续加工流程入口。

主要输入：

- 监管发文、通知、办法、接口标准、字段规范等文件。
- 文件标题、发文机构、文号、发布日期、来源链接、适用领域等元数据。

主要处理：

- 文件上传与存储。
- 文本解析与正文抽取。
- 解析摘要生成。
- 创建规则加工任务。
- 生成文档级任务画像，包括文件类型、候选领域、疑似影响方向和建议处理路线。

主要输出：

- 监管制度记录：登记监管材料台账，保存标题、发文机构、文号、发布日期、来源链接、适用领域、文件状态和原始文件地址。
- 解析文本：保存从原始文件中抽取出的机器可处理文本，包括正文、标题层级、表格内容、附件内容及页码/段落位置，作为条款切分和语义识别的原文底座。
- 待加工任务：启动并跟踪一次监管规则加工流程，记录当前步骤、处理状态、异常信息、复核状态和后续产出。

任务创建边界：

```text
创建待加工任务 != 生成最终影响结论
```

首期建议只要文件上传成功且解析出有效文本，就创建待加工任务。任务创建阶段可以引入 LLM 做文档级初筛和任务画像，但该结果只作为后续处理输入，不作为最终影响判断。

LLM 在该阶段可输出：

- 文件类型：通知、办法、接口规范、字段标准、业务规则等。
- 监管主题：1104、EAST、客户风险、一表通、区域特色报表、数据治理等。
- 候选影响方向：报表结构、报送字段、指标口径、机构范围、频度时限、校验规则、数据质量、血缘影响等。
- 建议处理路线：完整影响分析、轻量入库、人工确认。
- 初步判断依据：引用解析文本中的原文片段说明原因。

最终是否影响报送落地，应放在后续影响分析阶段，结合变更证据、报送对象定位、指标口径、数据血缘、历史工单经验和人工复核共同确认。

当前相关接口：

```text
POST /api/documents/upload
GET  /api/documents
POST /api/tasks/from-document/{document_id}
```

### 4.2 变更证据

目标：从解析全文、表样、填报说明、会议纪要和历史工单中识别出后续需要处理的候选监管报送变更证据，形成可追溯的证据工作集。

这一步不再只关注普通条款切分。对于监管报送项目，证据可能来自：

| 证据类型 | 示例 | 处理重点 |
|---|---|---|
| 条款证据 | 通知正文、制度条款、监管答疑 | 识别义务、范围、时间、适用主体 |
| 表样证据 | Excel/WPS 报表行列项目变化 | 识别新增、删除、改名、位置变化 |
| 填报说明证据 | Word/PDF/WPS 口径说明 | 识别指标定义、统计范围、排除项、特殊说明 |
| 会议纪要证据 | 监管会议说明、业务讨论纪要 | 识别人工解释、待确认问题和最终口径 |
| 历史工单证据 | 需求、开发、测试、验收记录 | 复用历史映射、改造点和验收口径 |

推荐采用：

```text
确定性解析
  -> 识别候选变更证据
  -> AI 结合报送体系目录筛选有处理价值的证据
  -> 保存证据类型、原文/表格位置、候选报送对象和候选变更类型
  -> 人工复核兜底
```

证据筛选重点从“是否和业务对象相关”调整为“是否可能影响监管报送对象、报送项、指标口径、机构范围、频度时限、数据源、校验或工单”。

主要输出：

- 证据类型：条款、表样差异、填报说明差异、会议纪要、历史工单。
- 原文或表格位置：页码、段落、sheet、行列坐标、附件名称。
- 候选报送体系：1104、EAST、客户风险、一表通等。
- 候选报送对象：报表、明细表、主题域、分部。
- 候选报送项：指标单元格、行列项目、明细字段、维度项。
- 候选变更类型：新增、修订、停报、口径调整、机构范围调整、频度调整、校验调整。
- 入选原因和证据复核状态。

当前一期实现接口：

```text
POST /api/reporting/seed-1104
GET  /api/reporting/objects?reporting_system_code=1104
GET  /api/reporting/items?reporting_system_code=1104
GET  /api/reporting/items/{item_code}/lineage
```

证据切分、表样差异和会议纪要证据仍是后续增强点，当前一期先用文本规则识别 1104 报表和指标变更。

建议后续补充：

```text
POST  /api/reporting/evidence/extract
PATCH /api/reporting/evidence/{evidence_id}/review
```

### 4.3 语义识别与影响分析

目标：先将变更证据转为结构化监管报送语义，再定位到具体报送对象、报送项和指标口径，最后结合血缘库判断受影响的报送系统字段、源系统字段、加工逻辑、校验规则和工单类型。

本阶段采用以下设计基线：

```text
变更证据
  -> AI 抽取报送体系、报送对象、报送项、监管动作和口径描述
  -> 后端用报送体系目录和版本库校验候选对象
  -> 后端召回报送项、指标口径、历史案例和数据血缘
  -> AI 基于可信候选解释影响原因、待确认问题和建议工单
  -> 后端保存结构化影响项
  -> 人工复核确认
```

关键边界：

| 环节 | 责任方 | 边界 |
|---|---|---|
| 报送语义识别 | AI | 识别报送体系、报送对象、报送项、监管动作、口径描述、机构范围和时间要求 |
| 候选校验 | 后端 | 用 `reg_reporting_*` 目录、版本和别名表校验候选对象是否存在 |
| 血缘召回 | 后端 | 根据报送项查询已确认或候选血缘，不允许 AI 发明内部表字段 |
| 影响解释 | AI | 只能基于原文证据、后端候选报送项和血缘候选生成影响说明 |
| 结果保存 | 后端 | 保存结构化影响项、置信度、证据、待确认问题和工单草稿 |

推荐的主流程：

```text
监管变更证据
  -> 识别报送体系
  -> 识别报送对象
  -> 识别报送项/指标/字段
  -> 识别口径差异
  -> 召回报送项血缘
  -> 定位报送系统字段和源系统字段
  -> 分析影响类型
  -> 生成分层工单
  -> 沉淀人工确认经验
```

字段元数据和业务对象仍然重要，但它们是血缘和口径分析的一部分，不再是影响分析入口。系统不能从全文直接让 AI 猜内部字段；必须先命中报送体系和报送项，再由后端查出报送字段、源系统字段、加工任务和校验规则候选，最后让 AI 在可信候选范围内解释影响。

#### 4.3.1 报送项定位逻辑

不同报送体系的定位粒度不同：

| 报送体系 | 定位粒度 | 示例 |
|---|---|---|
| 1104 | 报表编号 + 分部 + 行项目 + 列项目 + 指标/单元格 + 版本 | G24 最大百家金融机构同业融入余额 |
| EAST | 主题域 + 明细表 + 字段名 + 版本 | 贷款合同表合同编号 |
| 客户风险 | 主体 + 风险暴露维度 + 报送字段 | 集团客户授信额度 |
| 一表通 | 资源层明细项 + 穿透层宽表字段 + 指标层加工项 | 客户/业务/账务明细到监管指标 |

首期 1104 的定位顺序：

```text
报表编号
  -> 报表名称/别名
  -> 分部或附注
  -> 行项目/列项目
  -> 指标口径
  -> 版本和机构范围
```

示例：

```text
监管材料：调整最大百家金融机构同业融入余额统计口径
候选报送对象：G24、G21、G27
候选报送项：最大百家金融机构同业融入余额、同业存放余额、30 日内流动性期限缺口
待确认问题：是否影响存量追溯、交易对手金融机构认定、同业产品范围、剩余期限维度
```

#### 4.3.2 血缘定位逻辑

血缘定位采用多段映射：

```text
监管报送项
  -> 报送系统字段
  -> 报送加工表/结果表
  -> 数据集市/主题宽表字段
  -> ODS/贴源字段
  -> 源系统表字段
  -> 码值/主数据/维度表
  -> ETL/调度任务/校验任务
```

示例：

```text
G24.最大百家金融机构同业融入余额
  -> rpt_g24.interbank_borrowing_bal_top100
  -> dm_interbank_position.balance
  -> interbank_deal.balance
  -> interbank_deal.counterparty_fin_org_code
  -> counterparty.institution_type
```

每条血缘边必须保存证据：

| 证据类型 | 示例 |
|---|---|
| SQL/ETL 解析 | 加工任务、调度脚本、存储过程 |
| 数据字典 | 报送系统字段、源系统字段、码表定义 |
| 人工确认 | 会议纪要、确认邮件、工单结论 |
| 历史案例 | 以往同类指标变更处理记录 |

#### 4.3.3 历史经验相似检索

首期不强依赖 RAG，先采用结构化表相似检索。历史影响项、工单、校验规则、字段映射和人工确认结论结构化存储在数据库中；当前变更由 AI/规则抽取成结构化特征后，由后端固定查询逻辑召回相似历史案例。

AI 不直接生成 SQL，也不直接访问数据库。

职责分工：

| 环节 | 责任方 | 输出 |
|---|---|---|
| 变更语义理解 | AI | 报送体系、报送对象、报送项、监管动作、口径描述、候选影响类型 |
| 特征合法性校验 | 后端 | 校验是否属于已有报送目录、版本、别名、指标或字段映射 |
| 历史案例候选召回 | 后端 | 使用固定查询模板或 ORM 查询已确认历史影响项和工单 |
| 相似度计算 | 后端 | TopN 相似历史案例、分数和结构化相似原因 |
| 影响判定解释 | AI | 结合当前证据和 TopN 历史案例生成自然语言解释 |
| 最终确认 | 人工复核 | 确认是否进入工单草稿、规则沉淀和经验归档 |

AI 输出的不是 SQL，而是结构化检索特征，例如：

```json
{
  "reporting_system": "1104",
  "reporting_objects": ["G24", "G21", "G27"],
  "reporting_items": ["最大百家金融机构同业融入余额"],
  "regulatory_actions": ["调整口径"],
  "impact_types": ["指标口径影响", "加工逻辑影响", "校验规则影响"],
  "candidate_dimensions": ["交易对手金融机构", "同业产品类型", "余额", "剩余期限"]
}
```

后端只基于这些已校验特征进行候选召回。首期评分维度建议包括：

| 匹配项 | 用途 |
|---|---|
| 报送体系 | 是否属于同一报送体系 |
| 报送对象 | 是否命中同一报表、表页、明细表或主题域 |
| 报送项 | 是否命中同一指标、字段、行列项目 |
| 监管动作 | 是否同为新增、修订、口径调整、校验调整等 |
| 影响类型 | 是否影响同类口径、源字段、加工任务或校验规则 |
| 历史确认状态 | 优先参考已确认、已验收、已归档案例 |

首期推荐结果：

```text
当前变更证据
  -> AI 输出结构化特征
  -> 后端校验特征
  -> 后端召回候选历史影响项/工单/映射
  -> 后端计算相似度 TopN
  -> AI 基于 TopN 解释影响判定和待确认问题
  -> 人工复核确认
```

RAG 作为二期增强能力，仅在历史材料、旧工单、会议纪要数量增加，结构化字段召回不足或需要语义相似召回时引入。

#### 4.3.4 影响判定逻辑

系统不能只靠“是否命中报表编号”判断有用。需要区分：

| 概念 | 含义 | 后续动作 |
|---|---|---|
| 相关证据 | 提到某报送体系、报表、字段、指标或口径 | 进入候选定位 |
| 有影响证据 | 可能需要报送项、口径、字段、加工、校验或任务调整 | 进入复核和影响分析 |
| 可落地影响项 | 能转成口径确认、数据映射、开发、校验或测试工单 | 生成工单草稿并沉淀经验 |

真正影响报送落地的基本条件：

```text
监管材料提出明确变更或解释
+ 该变更属于目标报送体系或可扩展报送体系
+ 能定位到报送对象、报送项、指标口径或机构范围
+ 能召回报送系统字段、源系统字段、加工任务或校验规则候选
+ 存在确认、改造、校验、测试、报送或归档动作
```

#### 4.3.5 影响判定维度

| 判断维度 | 说明 | 示例 |
|---|---|---|
| 报送体系匹配 | 是否属于 1104/EAST/客户风险/一表通等目标体系 | 1104、EAST |
| 报送对象定位 | 是否能定位报表、明细表、主题域或分部 | G24、G21、EAST 贷款合同表 |
| 报送项定位 | 是否能定位具体指标、行列项目或字段 | 最大百家金融机构同业融入余额 |
| 口径变化 | 是否影响统计范围、过滤条件、排除项或码值 | 交易对手金融机构认定变化 |
| 血缘命中 | 是否命中报送字段、源字段、ETL 或校验规则 | `rpt_g24.interbank_borrowing_bal_top100` |
| 历史样例命中 | 是否能召回相似影响项、历史工单或人工结论 | 上次 G24 同业融入口径调整工单 |
| 可落地动作 | 是否能形成确认、改造、校验、测试或归档动作 | 口径确认工单、报送加工工单 |

#### 4.3.6 处理结果分类

| 结果 | 含义 | 后续动作 |
|---|---|---|
| 明确影响 | 变更明确，且命中已确认报送项和血缘 | 生成实施工单 |
| 可能影响 | 命中候选报送项或候选血缘，但证据不足 | 生成人工确认工单 |
| 仅作参考 | 有背景价值，不触发系统改造 | 归档 |
| 不相关 | 不属于当前报送体系或机构范围 | 过滤 |
| 待补充材料 | 需要会议纪要、监管答疑或人工口径补充 | 挂起并提示补充 |

推荐前端展示：

| 证据 | 判定 | 命中报送对象/报送项 | 处理建议 |
|---|---|---|---|
| 填报说明第 3 条 | 明确影响 | G24 最大百家金融机构同业融入余额 | 生成口径确认和加工工单 |
| 表样新增列 | 可能影响 | G21 期限缺口相关列 | 人工复核字段映射 |
| 会议纪要说明 | 待补充材料 | G25 候选指标 | 补充监管答疑 |
| 背景段 | 仅作参考 | 无 | 归档 |

### 4.4 规则与工单

目标：将明确影响项沉淀为可复用报送规则、血缘映射和工单草稿，并进一步生成可供口径确认、开发拆解、测试验收和经验归档使用的分类型工单。规则与工单不是首期唯一目标，而是影响分析结果的沉淀与落地辅助。

监管报送场景下，工单不应只等于 SQL 工单。SQL 仍然有必要，但应作为“报送加工工单”或“校验规则工单”中的技术内容，而不是唯一产物。

推荐工单类型：

| 工单类型 | 责任方 | 内容 |
|---|---|---|
| 口径确认工单 | 监管报送/业务人员 | 确认指标含义、适用范围、是否追溯、特殊口径 |
| 数据映射工单 | 数据治理/报送人员 | 确认报送项到报送字段、源字段、码值维表的映射 |
| 报送加工工单 | 报送系统/数据开发 | 修改 SQL、ETL、调度、汇总逻辑 |
| 源系统改造工单 | 源系统团队 | 新增采集字段、调整码值、补充接口 |
| 校验规则工单 | 数据质量/报送团队 | 新增或修改表内、表间、跨体系校验 |
| 测试验收工单 | 业务 + 科技 | 准备样例、回归测试、差异分析、验收确认 |
| 归档复盘工单 | 报送管理人员 | 记录最终口径、处理结论、监管反馈和经验 |

工单草稿应包含：

| 内容 | 示例 |
|---|---|
| 工单标题 | 【1104-G24】最大百家金融机构同业融入口径调整影响分析与报送字段改造 |
| 监管依据 | 关联监管制度、条款编号、表样位置、填报说明片段、会议纪要 |
| 涉及报送体系 | 1104 |
| 涉及报送对象/报送项 | G24，最大百家金融机构同业融入余额 |
| 当前血缘定位 | 报送字段、源系统字段、加工任务、维表码值 |
| 影响类型 | 指标口径影响、加工逻辑影响、校验规则影响 |
| 建议处理动作 | 口径确认、SQL/ETL 修改、差异分析、回归测试 |
| 待确认问题 | 存量是否追溯、交易对手金融机构识别是否按主数据最新口径、同业产品范围是否调整 |
| 验收标准 | 新旧口径差异可解释，样例机构回归通过 |
| 审核状态 | 待业务确认、待合规确认、待技术确认 |

当前相关接口：

```text
POST /api/tasks/{task_id}/generate-ticket
GET  /api/tasks/{task_id}/workflow
```

建议后续补充：

```text
GET   /api/tasks/{task_id}/ticket-drafts
PATCH /api/ticket-drafts/{ticket_id}
PATCH /api/reporting/impact-items/{impact_item_id}/review
```

建议工单结构：

```text
一、监管背景
二、变更依据
三、涉及报送体系、报送对象和报送项
四、当前血缘定位
五、影响类型和影响原因
六、建议处理动作
七、SQL/ETL/校验建议
八、测试要点与验收标准
九、待确认问题和归档要求
```

建议新增或增强：

| 接口 | 作用 |
|---|---|

首期已经完成 reporting catalog、workflow 聚合、影响分析和工单草稿生成接口。证据切分、表样差异、人工复核状态和历史案例召回留到下一轮。

历史经验检索的后端原则：

```text
AI 不生成 SQL。
AI 只输出结构化检索特征和影响解释。
后端使用固定查询模板或 ORM 查询报送目录、血缘和历史案例。
后端负责候选召回、相似度打分、权限控制和状态过滤。
AI 只基于后端返回的可信候选做影响判定解释。
AI 不直接发明内部表字段，不直接发布生产 SQL。
```

## 8. 对外汇报表述

推荐表述：

> 本项目不是简单的监管发文摘要工具，而是面向监管报送变更的影响分析与落地辅助平台。系统将监管公告、表样、填报说明和会议纪要中的变更要求，定位到具体报送对象和报送项，再结合内部报送系统字段、源系统血缘、历史工单经验和校验规则，生成可复核的影响分析和分类型工单草稿，帮助减少反复人工沟通，并把人工判断经验沉淀为可复用的监管报送知识资产。

更短版本：

> 以 1104 为一期样板，构建一套可扩展到 EAST、客户风险和一表通的监管报送变更影响分析框架，核心能力是“报送项定位、血缘穿透、影响判断、工单生成、经验沉淀”。
